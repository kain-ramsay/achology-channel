## 2. The design-surface standard (ruled S258, canonical in standing rule 16)

One dividing question decides where a visual decision lives: does the built theme already hold the thing?

- **Not yet held** (a new component, a new direction): Chat renders it in the side panel to the render standard and Kain rules there.
- **Already held**: you render it and Kain judges the real thing live in Safari, never a reconstruction. Your live design sessions with him are this surface working as intended.

**The render standard** (what any render must meet before it earns Kain's eye): every word real (approved copy, sourced data, or a named proposal); shown at true size with surroundings present, a repeated element always shown repeating (a card as a populated grid of at least six real items, at desktop, tablet and phone widths); exactly one open question; options rendered identically on the same content; self-critique run first.

**The fold-back** (your Rule 14, tightened at v2.9): whoever rendered the approved artefact writes the signed record. When Kain approves how a component looks on the live page, you export the approved state into that component's design folder as the prototype's next version, update the build sheet to match, and your RULING file names both writes, in the same session. A Safari approval left as a RULING file with no prototype version behind it is now the same harness break as an unfiled ruling. This keeps your Rule 4 chain complete: prototype wins, sheet matches prototype, code matches sheet, whichever surface the ruling happened on.
