## READ THIS FIRST: page_gate reports two checks that cannot fail

`page_gate` reaches the build site through a local mirror, because SiteGround's antibot answers every automated request with a challenge. The mirror lives in page_gate.py. `fetch_through_server()` runs `curl -sk --max-time 30 -o /tmp/.pg_body -w '%{content_type}'` and captures only the body and the content type: **the HTTP status is never captured.** `MirrorHandler.do_GET()` then calls `self.send_response(200)` unconditionally for every path it serves.

Verified this session rather than reasoned:

1. Asked from inside the origin, `/courses/`, `/pricing/`, `/accreditation/`, `/about/founders-letter/` and a nonsense control path all return **404**; `/about/` and `/help/` return 200.
2. Through the mirror, every one of those becomes **200**.
3. So check 14, links-resolve, printed "49 checked, all resolve" for a page that links to six destinations which do not exist. Confirmed independently in a real browser on the live origin: `/about/founders-letter/`, `/academy/schools/`, `/accreditation/`, `/courses/`, `/free-events/` and `/pricing/` all return 404, and `/membership/` 301s to a help article.
4. Check 13, assets-load, is blind the same way: the browser loads every asset through the mirror, so a missing image would arrive as HTTP 200 carrying a 404 page's bytes, and "nothing failed" would still print.

Check 13 is the check DSRD 6 §11 exists for. Its opening sentence: "a page was once confirmed as 675 elements pixel-identical to its approved design while every image on it was silently failing to load". **The instrument built to stop that happening again cannot see it happening.**

Scope of the damage: every record filed to date that cites "assets-load: nothing failed" or "links-resolve: all resolve" is unverified on those two rows. That is the nine policy-family records, the Policies index record, and this one. No other row is affected: the geometry, metadata, dash and width rows read the page's own DOM and stand.

Instrument changes are yours to rule, as ruling 8 was. My proposed amendment, ready to build on your word: `fetch_through_server()` also captures `%{http_code}` and returns it; `MirrorHandler` replays that status instead of a hardcoded 200; the script is versioned v3 in its header; and every page already walked is re-gated so the two rows are filled honestly. I have not touched the script. **Marked: waiting on ruling.**

## The spec collisions this page raises

1. **The en dash ban versus the timeline spec.** DSRD 2's ban is absolute: "No em dash (U+2014) and no en dash (U+2013) appears anywhere in Achology copy: page copy, articles, headings, metadata, captions, CSV fields and emails alike, across every page and content type this document specifies, with no exception. Use a colon, a comma, brackets or a full stop instead." DSRD 9 §23 specifies the timeline's era dates **with en dashes**, twice, and the characters are described here rather than reproduced, because pasting them would fail this file's own gate: the at-rest state line gives the era name and then the year range written as 2012, a U+2013, 2014; and the era table's first row repeats the same range in the same form. Both sit in DSRD 9 §23, at the era-state table and the era palette table. The built page follows DSRD 9 verbatim and therefore fails DSRD 2. None of the ban's four permitted substitutes reads correctly in a date range, so the remedy is a wording decision rather than a character swap. Reported and stopped, per Rule 8.

2. **The phone spacing tier has no mechanism.** DSRD 7 §4.3 says "On phones (below 768px) both measurements become 32px. Use `var(--sp-2xl)`, whose standard mobile reduction produces exactly this behaviour." **No such reduction exists.** `--sp-2xl` is defined once, at base.css line 84, as 48px, and is never redefined at any breakpoint. The reduction the sentence describes belongs to a utility class (`.sp-2xl { padding: var(--sp-xl) 0 }`), not to the token. Pages that conform do so through hand-written phone tiers. On this page four block separators consequently keep 48px at phone where ruling 4 demands 32: `.pfq`, `.tw-wrap` at both edges, `.policy-body--ruled + .policy-body--ruled` (the row the gate caught), and `.help-popular`. Two are also uneven at desktop, running 48 above the line and 32 below where ruling 4 demands 48/48.

3. **Why none of that was fixed.** Two of the four separators are shared. `.policy-body--ruled + .policy-body--ruled` also fires on the Testimonials page, whose template stacks two of those wrappers adjacently at lines 57 and 65, which the rule's own code comment denies. `.help-popular` renders on help articles, the 404 and the policies index. Correcting either touches pages beyond this one, which under Rule 3 needs a signed sweep brief naming them. **Requested: a sweep brief for phone-tier conformance across the shared separators.** Marked: waiting on ruling. The components.css comment claiming no other template stacks the wrapper should be treated as false; it is the exact failure mode Rule 4 exists for.
