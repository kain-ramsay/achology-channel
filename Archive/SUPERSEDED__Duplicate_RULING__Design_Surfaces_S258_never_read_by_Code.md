## 2. The design-surface standard (ruled S258, canonical in standing rule 16)

**The two surfaces.** The dividing question for any visual decision is: does the built theme already hold the thing? If it does not yet exist (a new component, a genuinely new direction), Chat renders it in the side panel and Kain rules there. If the theme already holds it, you render it and Kain judges it live in Safari, never a reconstruction. Your live design sessions with Kain in Safari are legitimate Safari rulings, not breaches: Kain confirmed this pattern stays, so long as it remains consistent practice.

**The render standard.** A render earns Kain's eye only when all five checks pass: every word in it real (approved copy, sourced data, or a named proposal, never filler); shown at true size with surroundings present (a component inside its block, a block inside its page, a card always as a populated grid of at least six with six different real titles and blurbs at true lengths, at desktop, tablet and phone widths); answering exactly one question with everything else held at approved state; every option rendered the same way on the same content with one variable changed; self-critique run and problems fixed before presenting.

**The fold-back.** Whoever rendered the approved artefact writes the signed record. When Kain approves in the panel, Chat saves the prototype and writes the build sheet. When Kain approves live in Safari, you export the approved state as the prototype's next version, update the build sheet to match, and file a RULING through this channel naming both writes, in the same session. Either way Chat records the ruling in DSRD 8 at close. A live approval that never folds back becomes a second, disagreeing definition of the same truth, which is exactly what the S257 precedence system exists to prevent.
