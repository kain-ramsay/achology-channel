# Job 3: read-only code review of the Achology WordPress theme

Code reviewed: repository root PHP and JavaScript files at commit `c1fa480` (previews, tools and harness folders ignored; `data/` and `policies-content/` are not in the root, so they are out of scope except where a root file includes them).

Method: every root `.php` and `.js` file was read in full by eight reviewers working in parallel, each told to verify line numbers and to say "cannot tell from the code" rather than guess. `php -l` passed on every PHP file reviewed and `node --check` passed on every JS file. Nothing was run in a browser or against a live WordPress, and no database or server config was available. No existing file was changed. The one SERIOUS finding was re-checked by hand against the code.

Counts are of finding bullets below. Cross-cutting items are counted once, where they are listed under "Cross-cutting"; per-file bullets that only point at them (marked "see Cross-cutting") are also counted as their own bullets, so the totals slightly overstate the number of distinct defects.

Headline: the admin files you named (`rank-math-feed.php`, `reviews-import.php`, `media-library.php`, `academy-admin.php`, `card-review.php`, `commerce-cards.php`) have no exploitable hole. They check `manage_options` or `edit_pages` where they act, use `check_admin_referer` on the import and reset, prepare their one query with variables, and escape their output. They have no nonce-less handler of their own. The one SERIOUS item is a front-end page-breaking bug in `functions.php`/`course.js`. The theme registers no AJAX or admin-post handler anywhere, and its one REST route is a public read-only GET.

Grades: **SERIOUS** = exploitable hole or something that breaks a page. **SHOULD FIX** = wrong or fragile today, or a hole that needs a privileged account or a future change. **MINOR** = low risk, hygiene, or cost that is small today.

Where several files share one defect (JSON-LD without `JSON_HEX_TAG`, no `ABSPATH` guard, hard-coded community invitation URL) it is described once under "Cross-cutting" and each file lists its own line numbers.

## Cross-cutting

- **SHOULD FIX** JSON-LD blocks built with `JSON_UNESCAPED_SLASHES` and no `JSON_HEX_TAG`: `page-about.php:797`, `page-pricing.php:219,236`, `template-policy.php:537,551`, `template-policies-index.php:298,318`, `single-article.php:1263,1280`, `single-book_note.php:1675-1678,1735`, `single-faq_article.php:899,915`, `taxonomy-kh_category.php:168-202`, `course-parts.php:1062-1063`, `rank-math-feed.php:264`. A `</script>` inside any string value ends the script block (confirmed by running PHP). Where the string is baked into the theme it is harmless; where it comes from the database (page titles, ACF text fields) it is stored XSS for any account that can edit those fields. Cannot tell from the code which roles can edit the book-note ACF fields. Safe version: `wp_json_encode( $data, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE | JSON_HEX_TAG | JSON_HEX_AMP )` on every `application/ld+json` echo.
- **MINOR** No `if ( ! defined( 'ABSPATH' ) ) { exit; }` in many files (the PHP template files, `courses-setup.php`, `faq-setup.php`, `knowledge-hub-setup.php`, `people-setup.php`, `reviews-setup.php`, `commerce-cards.php`, `card-review.php`, `shared-parts.php`, `course-parts.php`). A direct request fatals on an undefined function and may print a file path if `display_errors` is on; cannot tell from the code whether the server blocks direct `.php` access or hides errors. Safe version: add the standard guard after the docblock.
- **MINOR** The community invitation URL with an `invitation_token=` value is hard-coded in at least `header.php:110,341`, `help-parts.php:78,113`, `shared-parts.php:1334`, `pricing-parts.php:78`, `template-policy.php:341`. Cannot tell from the code whether the token is public by design or can be rotated. Safe version: one constant or helper so a rotation is a one-line change.

## reviews-import.php

Loaded only on `is_admin()` (`functions.php:143-145`). Every entry point checks `manage_options` (659, 741, 749); reset (673) and import (683) use `check_admin_referer` with separate actions; the one `$wpdb` query with variables is prepared (527); no upload, unserialize, remote fetch or CSV export; the redirect at 675 is `wp_safe_redirect` to a fixed admin URL.

- **SHOULD FIX** `reviews-import.php:491-544` (unchecked bulk insert at 573) — "Safe to run twice" fails if a request dies mid-batch: the post row is inserted at once but its meta, including the `_ach_review_key` fingerprint, is buffered and written up to about 50 reviews later, so a timeout leaves published `review` posts with no meta and the next run imports those rows again. A failed insert (519-522) is also reported as "skipped". *Safe version:* write each post's meta straight after its insert (or a transaction if InnoDB; cannot tell), check the bulk INSERT's return and stop with a notice, and count insert failures separately.
- **SHOULD FIX** `reviews-import.php:658-708, 445-561` — No lock against two simultaneous runs; both read the same fingerprint list (449) and both insert, producing duplicates. *Safe version:* `if ( get_transient( 'ach_review_import_lock' ) ) { return; } set_transient( 'ach_review_import_lock', 1, 60 );` and delete it at the end.
- **SHOULD FIX** `reviews-import.php:552` — `wp_cache_flush()` after every batch (about once a second) empties the whole site's object cache on a host with a persistent cache. *Safe version:* `wp_cache_delete( _count_posts_cache_key( 'review' ), 'counts' ); wp_cache_set_posts_last_changed();`.
- **SHOULD FIX** `reviews-import.php:889, 934` (and `functions.php:137-141`) — The admin text says reviews are drafts ("Every review is a draft that nothing links to...", button "Import all reviews as drafts") but the code publishes them (`'post_status' => 'publish'`, line 500), so you are told the wrong thing before confirming a 4,500-review import or reset. *Safe version:* correct the three strings, or import as drafts if that was the intent.
- **SHOULD FIX** `reviews-import.php:335-342, 415, 498` — The raw SQL insert bypasses kses and title sanitising, so student-written text, course name and title are stored unsanitised. Output is escaped (`reviews-setup.php:648` onward), so there is no live XSS. *Safe version:* `sanitize_textarea_field`, `sanitize_text_field` and `wp_strip_all_tags` on the way in.
- **MINOR** `reviews-import.php:194` — `fgetcsv()` without the `$escape` argument is deprecated on PHP 8.4; cannot tell the production PHP version. *Safe version:* `fgetcsv( $h, 0, ',', '"', '' )`.
- **MINOR** `reviews-import.php:187` — The first line is discarded unconditionally as the PHP guard, so a CSV without a guard line loses its header row. *Safe version:* discard only if the line starts with `<?php`, else `rewind()`.
- **MINOR** `reviews-import.php:195-198, 144-147, 309-320, 361, 367` — Rows with a different column count are dropped silently and the readers assume every named column exists, so a re-export with a renamed column mis-imports silently. *Safe version:* validate the required headings and show an error.

- **MINOR** `reviews-import.php:812-814` — Each screen view loads all review IDs just to sample first, middle and last, and counts all statuses while the progress figure (779) counts only draft and publish. *Safe version:* `MIN(ID)`, `MAX(ID)` and one offset query.
- **MINOR** `reviews-import.php:925, 907, 85, 454` — The resume offset is set to the in-bank count, so if duplicates exist the offset overshoots and unimported rows are skipped; `ACHOLOGY_REVIEW_IMPORT_BATCH` only feeds an estimate while the real batch is a 20-second budget. *Safe version:* store the last completed offset in an option.
- **MINOR** `reviews-import.php:672-677` — The destructive reset is a GET; it is nonce and capability protected so not CSRF-exploitable, but the URL is reusable from history within the nonce lifetime. *Safe version:* a POST form with `wp_nonce_field`.

- **SHOULD FIX** `media-library.php:1026-1034, 1048-1062, 859-961` — Any upload whose file name matches an existing picture's name silently replaces that picture's file ("upgrade") with no `current_user_can( 'edit_post', $owner )` check, so an Author-level account could overwrite another user's library image (logo, share image); the same filters fire for any path through `wp_handle_upload`.
